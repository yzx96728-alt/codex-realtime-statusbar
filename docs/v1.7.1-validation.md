# v1.7.1 最小整改验证（未发布候选）

候选版本1.7.1／build9；稳定基线为v1.7提交`5e48bedd9785fe501dcd2805400b13c14ade9d41`。只在本地分支和`build/v1.7.1/`生成候选，未修改正式安装、Codex配置或handoff技能，未提交、推送或创建Release。

## 修复依据与行为

- 审计发现压缩后输入／输出均为0，而上下文总量为49,702及50,301。现在仅在已确认`compacted`后将此模式识别为基线；普通请求、基线、等待基线及未知口径分开。缺失数值为未记录，不补0；基线不显示为最近请求，不以输入0推断上下文0。
- 连续广播按累计和最近用量完整结构、容量、会话、任务开始序号、压缩周期及可用响应ID判重。重复广播可更新额度快照及其时间，但保留原用量时间和事件ID，不获得新提醒资格。相同最近用量但累计增长、任务变化或响应ID不同会被保留。
- `compacted`立即清除旧周期待提醒，等待后续有效上下文记录；不推断自动／手动。`turn_aborted`为取消，不能成为正常完成；完成事件须匹配当前根任务，已取消任务的迟到完成也不触发提醒。
- 待提醒绑定会话、任务、周期及用量事件。保留65%／70%和低于55%重置。扫描中记录可去重的低占用证据，避免压缩基线与新请求都落在两次轮询之间时漏重置，也避免每次重读历史低占用都重置。
- JSONL改为后台串行分块扫描，读取入口文件长度内的完整行。以聊天ID、路径和请求版本核对返回值；切换后旧结果不更新快照。文件读取失败清空显示；不完整末行留待下次追加后再读。

## 验证结果

- 完整测试：Core、Following、Localization、UsageEvent四组Swift测试及5项Python隔离安装测试通过。
- 新结构化模拟覆盖：零输入／输出但非零总量基线；重复广播不刷新时间；同用量真实请求（累计增长、响应ID或任务变化）；8毫秒压缩基线；旧待提醒失效；取消及迟到完成；任务／周期不匹配；低占用基线在两次轮询之间；重启及1.6／1.7状态迁移；实际追加换行；读取失败；9MiB普通单行和9MiB压缩记录；超限与损坏记录；串行后台读取返回期间切换聊天，以及A→B→A版本回绕防护。
- ARM／Intel通用构建及整包严格签名校验通过。仅交叉编译Intel，未做Intel实机验证。候选未启动GUI或替换安装，界面行为通过代码检查和回归测试验证。
- 候选的只读`--check`核对三份本机真实日志，大小约3.4／16.7／45.0MB，均有有效用量且无读取缺口；含两次压缩的样本能确认压缩。没有输出正文、聊天名称、会话ID或路径。
- 使用脱敏标识与模拟时间重放审计数值：49,702／475,000为10.4636%，50,301／475,000为10.5897%；均为压缩基线且不归零。
- 一次本机45MB日志读取约0.25秒（含命令行进程启动），不作为通用性能保证。完整读取仍有随文件增长的成本。
- 正式1.7安装可执行文件与原发布ZIP的SHA256与整改前一致，稳定产物保留可回退。

## 仍有的限制

- 上下文仍是结构化记录的估算，不是实时官方值、账户余额或精确成本；不辨别自动／手动压缩。
- 这不是完整增量引擎：日志变化后重新分块扫描全文件，但不在界面线程执行。文件仍在追加时本次只处理入口长度内的完整记录，下次轮询追上后续内容。
- 单行上限为16MiB；超限或相关损坏记录会显式标记状态不完整并暂停提醒，不静默猜测缺失事件。9MiB记录已测试；更大且超过上限的日志需要后续单独处理。
- 去重依赖日志实际提供的结构化身份与计数。若不同请求的所有计数、任务及可用响应身份都完全一致且没有任何边界事件，无法凭空证明它们不同，不通过时间戳猜新请求。
- 旧状态升级会清除待弹提醒并先建立基线；已显示档位保留，避免恢复旧提醒。已取消／未知状态不替代正常完成。
